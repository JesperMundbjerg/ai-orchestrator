# Design

Review Inbox is for projects that run for weeks, where agents need your judgement more often than they need your typing. Mission-control tools show you terminals. This one shows only the moments that need you, with the evidence to decide from, and routes your answer back to the conversation that asked.

This document describes current behavior and correctness rules. See [ARCHITECTURE.md](ARCHITECTURE.md) for the implemented module map, glossary, state lifetimes/recovery and provider matrix, [API.md](API.md) for the checked HTTP contract, and [ORCHESTRATION.md](ORCHESTRATION.md) for the repository adapter format. `http.ts` owns routing/guards **and** change-callback/reaction wiring today; reads such as `World.state()` still reconcile durable records, not just serialize a pure snapshot.

## What the UI talks to

**The UI talks only to the local service.** It uses HTTP for reads and actions and one SSE stream (`/api/events`) that says "something changed". It never talks to an agent, a harness or herdr.

This keeps the UI vendor-neutral. The service keeps three things per task:

| Kept | Why |
|---|---|
| **Harness** (`pi`, `claude`, `codex`, `manual`) | shown as a label; it picks the setup hint, never a code path in the UI |
| **Stable session id** (Pi: session file; Claude: `CLAUDE_CODE_SESSION_ID`; Codex: explicit thread id or `CODEX_THREAD_ID` when exported; else the herdr pane resolved to its agent session) | the reply's address. It survives restarts, and it is the same id herdr reports, so presence joins on it |
| **Capabilities**, learned from behaviour | what the UI branches on |

A Pi session's id is the **absolute path of its `.jsonl` file** (as the extension registers it and herdr reports it), never the id in the file's header. Anything submitting on a Pi agent's behalf, such as a daemon using `inbox --harness pi --session <path>`, must use that path: a reply is handed only to the session id it was submitted under, so the header id names a session nobody listens to.

The reply route is **learned, not configured**:
- **live**: an integration has polled with `mode: "live"` in the last 15 s (the Pi extension). The reply appears in the running session within seconds.
- **boundary**: a hook has called (Claude Code Stop / UserPromptSubmit / SessionStart). The reply lands at the next turn boundary.
- **pull**: neither has happened. The reply waits for `inbox replies`, unless the session runs in a herdr pane (below).

A session without a live integration that sits idle would never see an answer: a hook hands replies over only at a turn boundary, and an idle agent reaches none until someone prompts it. So when herdr shows such a session (pull or boundary) idle or done, the office **types the reply into its pane**, in the words the hook uses. It is claimed before typing, so it is typed once, and while it is typed no hook or pull is handed it (the prompt itself fires Claude Code's UserPromptSubmit). It is `delivered` only once herdr sees the agent take the prompt up; if herdr cannot type it, it fails like any other delivery, back in Needs you with Retry. A reply a hook or `inbox replies` already collected is never typed.

The UI shows the route as one sentence under the answer area, so you know what "sent" means before you send.

**herdr is an optional terminal provider, including a delivery path.** With presence discovery enabled, the service reads `herdr agent list` for status (working / idle / blocked / done) again whenever herdr's socket reports a status change or a pane coming or going, with polling as the fallback. It uses `herdr agent focus` for **Open conversation**. An integration or a hook is the first route for a reply, since it is acknowledged by the session itself and ties the inbox to no multiplexer. Without herdr/discovery, core submission, integration/hook/pull replies and reports still work, but presence is unknown, focus is unavailable, terminal messages wait and pane/project/switch effects cannot complete without the provider.

Two things are typed into a pane instead: a reply to an idle session nothing else would hand it to (above), and a **message in the office** (below): your instruction to a team, or one agent to another. Neither can wait for a turn boundary an idle agent never reaches. Both are typed with `herdr agent prompt`, one prompt per agent at a time (your answer to something it asked first, as its own prompt, then the messages: see Messages below), under three guards: it is sent only when reconciled terminal presence is idle or done, herdr itself refuses an agent that is asking something, and herdr must see the agent start working within seconds for the delivery to count.

A reported `working` status is not trusted forever. The service samples the full visible pane (normally at most once per 30 seconds) only for queued recipients or agents observed working for three minutes. Three minutes of unchanged sampled content can make that presence `idle`, both for the office and the same guarded, batched delivery path. **Pi's live working editor border vetoes idle, even if its spinner and output are unchanged or its lifecycle signal says idle/done**; this includes retry, compaction and custom working labels. Pi recovery additionally requires the standard empty editor's two complete borders and context footer (including when herdr skips screen detection because it has lifecycle authority): quiet, cropped, draft-filled or unrecognized output is not proof of idle. Changed output, an unreadable pane, a session/status/authority change or a new prompt clears stale evidence; elapsed working time alone never makes an agent free. With no queued delivery, observation starts after three minutes working, so the earliest stale verdict is six minutes. Before claiming a pane message or fallback reply, the sender refreshes presence and bypasses the sample throttle for a fresh pane check; refusal leaves it queued, and an unreadable Pi idle pane is unknown, not free. `herdr agent prompt --until working` checks uptake **after** typing, not an idle guard. A founder message still queued after ten minutes shows its waiting age in the thread and is logged once per queued attempt. Tests: `test/message-status.test.ts`.

## The three item types

| Type | You get | Primary actions |
|---|---|---|
| **Decide** | the question as the title, what the agent needs and what happens if nobody answers, 2+ options with consequences, the agent's pick and why, screenshots | pick an option (plus an optional note) |
| **Decide, open question** | the same with no options: a question that has no fixed answers | write the answer (text required; the button says **Answer**) |
| **Try it** | what to check, a live preview or a walkthrough of pages (each checked for reachability and framing, shown at desktop or phone width), setup notes | open it, then **Approve** (an optional note) or **Needs changes** (a note saying what, required) |
| **Review milestone** | what was finished, evidence at the exact revision | Accept, or Request changes (text required) |

A decision has two or more options, or none. With none it is an **open question**: the answer is words (`answer`, worded to the agent as "Answer: …", and an empty one is refused), so a held question with no structured choices needs no invented ones. Exactly one option is refused, since it is not a choice, and a recommendation needs options, since it picks one. Revising by key works the same for both, and adding or removing the options makes a new revision that turns an answer written for the old one stale.

A try-it request is answered with the milestone's two actions, `accept` and `request_changes`, worded to the agent as "Approved" and "Needs changes". Approving does not update the task's last accepted milestone, since a try is not one. `tried`, what a try was answered with before, is no longer accepted; the replies that carry it stay in the database and the conversation reads "Tried it".

**Discuss** (free text to the owning agent), **Back of queue** (below) and **Later** (snooze 1 h / 3 h / tomorrow, or mark handled) are on every type. A choice never stops you writing more.

## Layout

- **Left rail**: Needs you / Working / Parked with counts; projects with waiting counts and pins; herdr status; key hints.
- **Queue** (Needs you): filter chips by type with counts. The sort is stated on screen: pinned projects, then items an agent is blocked on, then the longest waiting, then the items you sent to the back. `n` opens the next item, `j`/`k` move, `b` sends the open item to the back of the queue. Each card shows type, task · project, age, a thumbnail, owner and harness, and whether the agent is waiting.
- **Detail**:
  - The header shows owner, harness, live status and Open conversation.
  - Tabs appear only when they have content: Context (with the task brief), Screenshots (older revisions dimmed), Live preview (or Pages, a walkthrough: one live frame at a time with what to look at, Previous/Next and ← →, opened first when there are several; a page that is down or refuses framing says so with an open-in-tab link), Conversation (your replies with their delivery state and a Retry).
  - The answer area is pinned at the bottom.
- **Working / Parked**: one card per task with its brief (objective, latest decision, last accepted milestone, doing now, next milestone), its open items and Park / Open conversation. Parking hides a task's items from Needs you; it does not pause the agent.

The **task brief** is project memory for you rather than for the model. It is edited by hand, and updated when you pick an option or accept a milestone.

## Correctness rules

- **Stable ids.** An item is `(task, key)`. Resubmitting the same key with identical content changes nothing. Changed content becomes a new revision. For a milestone or try in a project worktree, its captured HEAD is part of the evidence: presenting a new commit with the same prose makes a new revision.
- **Stale answers are visible.** A reply carries the revision it answered. Answering an out-of-date revision is refused (409). A queued reply that a new revision overtakes turns `stale`, and the conversation says so.
- **Delivery is acknowledged.** A reply is `queued` until an integration claims it, and `delivered` only after that integration acks it, or, for a reply the office types into a pane, after herdr sees the agent take it up. A reply is typed at most once and never both typed and handed over. If a claim has no ack after 30 s, the reply is shown as *uncertain*. A failed delivery returns the item to Needs you with Retry. Each send carries a client-made id, so a retried request never becomes a second answer.
- **Back of queue is ordering only.** The founder can move an item that needs them (`needs_attention`, nothing else) behind every other waiting one (`POST /api/items/:id/back-of-queue`, `items.backed_at`, the `item.backqueued` event). It is not an answer and not a snooze: the item stays in Needs you, the agent keeps waiting, no reply or delivery is created, nothing is typed anywhere, its age and `updated_at` are untouched, and no timer brings it back. The queue sorts backed items after everything else, whatever the pinned and blocking tiers say, in the order they were backed (a later backing goes behind an earlier one, and backing the last item again keeps it last; the service makes each `backed_at` strictly later than any before it). A **revision** by the agent keeps its place at the back, since the founder chose to look at it later and a revised item is not a reason to look sooner (the revision still turns an unsent answer stale as usual); a **newer item**, including a new item from the same agent, goes before every backed one. The place ends, and the item returns to its ordinary position, when the item is answered, snoozed, marked handled or withdrawn: a snooze that wakes, or a failed delivery that returns the item to Needs you, is an ordinary item again. **Pinning** a project also brings its backed items forward to their ordinary place (pinned projects sort first). The office's queue on the clearing and the decision sheet use the same order. Backing the only waiting item changes nothing and the UI does not offer it. Tests: `test/back-of-queue.test.ts`.
- **Approve all is an explicit, persisted inbox-only rule, off by default.** It is one of three modes of one setting (Off, Approve all, QA answers; an Approve all that was on before QA answers existed stays Approve all). Turning it on answers eligible waiting items (including snoozed/parked ones); new submissions and revisions are answered while it stays on, even with the UI closed and after a restart. It accepts only milestones and try-it requests, or chooses a decision's unambiguous recommended option, using the same leading-label/id interpretation as the UI. Never an open question, never a decision without a clear recommendation, **never an item a pipeline run presented for its “Founder approves” step** (its run binding commits with the submission, so automation already sees it; it stays in Needs you and says why), and never anything outside the inbox: no harness switch, merge, work verdict or other delivery. Each auto-answer uses the ordinary answer path, revision/stale checks, a stable client id, queued delivery and acknowledgments; its history records `autoApproved` and its text tells both founder and agent “Auto-approved (approve all).” Failed or uncertain delivery still requires explicit Retry, never a second automatic answer to that revision. The header's lifetime count counts auto-answered revisions, not retries. These boundaries are tested.
- **QA answers: an office agent decides on the founder's behalf, never the service, and never automatically** (a deliberate change, at the founder's request, of “no reasoning agent in the middle”; `src/server/qa.ts`, migration 12, `test/qa-answers.test.ts`). The founder chooses an ordinary office agent as the QA agent and turns QA answers on. The service calls no model and judges nothing: it tells the QA agent with one ordinary office notice (at most one waiting to be typed), and the QA agent reads the question with `inbox qa next` and decides with `inbox qa answer`, choosing an option, answering an open question in words, accepting, or asking for changes, always with a reason and the learnings it used. Only the chosen agent's own session may answer, only while QA answers are on, and only a revision nobody has answered: **the first answer wins**, so a founder answer first refuses the QA answer. Its answer takes the ordinary answer path (revision/stale checks, the stable id `qa:<item>:<revision>`, queued delivery, acks), is recorded as the QA agent's (`replies.answered_by`, the history's `qaAgent`, logged as `system`), never as the founder's, and tells the asking agent so. The founder can **override** it on the same revision; the override reaches the agent marked as overriding. **What the QA agent has leaves Needs you only while it has it**: an item it may answer is marked `withQa` when the founder's inbox is read (not in the inbox projection the office itself uses) and only while the QA agent is online; when it is offline or no longer in the office, or the mode is not QA answers, the same items are the founder's again, with no timer, and the header always shows “N with QA agent”. Nothing is ever answered automatically, after a restart or otherwise. **Founder-only**, never offered to the QA agent and refused if it tries: a pipeline run's “Founder approves” step, a repair waiver, and the QA agent's own questions; a QA answer that reached one some other way counts as automatic and grants nothing. **Learning**: the QA agent keeps its learnings itself, one Markdown file each in an Open Knowledge Format v0.2 bundle at `learnings/` in the data directory (the service only creates an empty `index.md` and `log.md`, never overwriting); `inbox qa answers` hands it the founder's own answers (as asked at that revision, with what an override overrode), never Approve-all or QA answers, behind a cursor it moves forward with `inbox qa learned`.
- **The founder picks the QA agent's model; the office starts the agent and closes only what it started** (`src/server/qa-agent.ts`, migration 14, `test/qa-agent.test.ts`). The one picker, in Off (“Predict with”) and in QA answers, lists the crew catalog's harness, model and effort entries by label (for example “Opus 5.5 · medium (Claude Code)”), plus none; nothing outside the catalog starts. Picking one makes the office start a new agent itself the way it starts a project's lead (`herdr agent start` with the catalog's start flags, the inbox hook settings for Claude Code, and the QA guide with the learnings path as its appended system prompt). **It starts without file-editing tools**: Claude Code with `--disallowedTools Edit,Write,NotebookEdit`, Pi with `--exclude-tools edit,write`; Bash stays for `inbox` and its learnings, so this lowers the risk of a reviewer changing code rather than ruling it out (the launch argv is tested), named `qa-<model>-<hex>`, in a workspace of its own on the service's checkout (trusted, so no trust prompt). Only once it runs is it designated (`qa_agent_id`) and recorded as office-started (`qa_started`); it then works the existing `QA:` notice loop. While it starts nothing changes: the previous QA agent stays designated, QA answers wait for their agent (the setting applies once it runs and never if it does not), and the choice cannot change until the start finishes. **A failed start designates nothing**: its pane is closed again, the setting stays as it was and the header shows why. **Replacing** designates the new agent first, then closes the previous one only if the office started it, and only while its pane still runs that same agent; **none** clears the designation and closes an office-started QA agent. An agent designated otherwise (the API's `agentId`) is never closed, and designating one retires an office-started agent. An office-started agent that dies stays designated and shows offline: everything is the founder's, as for any offline QA agent. The service calls no model: herdr starts the harness, and the UI shows the catalog's labels without branching on vendors.
- **In manual mode the QA agent's answer is only a prediction: never a reply, never delivered, never an approval** (the founder's request, so the QA agent's agreement with them can be measured; `src/server/qa.ts`, migration 13, `test/qa-answers.test.ts`). With the setting Off and a QA agent chosen (its model picked in Off itself, “Predict with”, without ever turning QA answers on; choosing none stops predictions; its learnings bundle is prepared as in QA answers), it gets the same `QA:` notice and loop, and `inbox qa answer` records its decision in `qa_predictions` instead of answering: no reply, no `reply.queued` event, nothing for the asking agent, nothing a pipeline or waiver can read, and the item stays in Needs you exactly as without it. One prediction per revision, refused once anyone has answered that revision, so a prediction made after the founder answered never counts. It is compared with the founder's first deciding answer to that revision: the same action with the same choice, both accept, or both request changes is a match; another action or choice is a mismatch; two answers in words are judged by the QA agent (`inbox qa judge`, recorded once, required before `inbox qa learned` moves past that answer). The service judges nothing in words. The learn feed shows each prediction beside the founder's answer, a mismatch marked as strongly as an override. The founder sees a prediction only once they have answered its revision (collapsed in the item's history, “QA prediction (not sent)”), so it cannot bias them, and the header shows predicted, agreed of judged, and the rate. Approve all and QA answers are unchanged; a QA answer is never a prediction.
- **A pipeline approval is the founder's own decision on one revision, for one run.** It counts only for the run that presented that item revision, at the round, selection scope and intended bytes it was presented with; equal bytes in another run (an abandoned one, or another repository) never borrow it. The standing decision is the latest Accept or Needs changes on that revision: a later message is conversation and neither grants nor withdraws it, an approve-all answer never counts, and an answered item keeps an explicit Accept (or Withdraw approval) control. Runs, `done` and the delivery gate judge evidence with one evaluator, so Runs never shows a step done that the gate refuses, and shows the reason. Review receipts likewise belong to the run that handed the work round over. Tests: `test/pipeline-approval.test.ts`.
- **An active pipeline has a frozen workflow contract.** Its graph and source versions are captured at start; later skill edits or removal apply only to new runs. New runs refuse missing sources. A published-base update retains previously reviewed paths in the bytes fingerprint even when they leave the actual diff, preserving evidence only when their bytes and modes remain unchanged. New, changed or deleted bytes still invalidate evidence; receipts and approvals are never rewritten. Path guards inspect the actual diff. Tests: `test/pipelines.test.ts`.
- **A dev run is delivered when its exact candidate is published, never when the gate allows.** On read, an open, unarchived run with an active dev boundary becomes `delivered` (recording the ref and tip) only when its candidate commit is reachable from `origin/<integration branch>` (the local branch only in a repository with no remotes, and not while the candidate's own checkout has it checked out), that commit holds exactly the pinned intended bytes, and every step the boundary requires is done by the gate's evaluator. A candidate that reached dev without this run's steps leaves the run open, saying so. Tests: `test/pipeline-landing.test.ts`.
- **A failing check counts only as “fails as on base”, never as a pass** (the founder's decision to accept identical baseline failures). Check evidence records its command and exit code. A nonzero exit counts only beside a base record in the same step and round: the same command (trimmed), recorded with `onBase` against exactly the run's `candidate.base`, with the same exit code. The match is mechanical, on the recorded command and exit code; the office runs nothing and judges nothing. A base that passed while the candidate fails, another command, another exit code or another base (after a re-base) is refused by the same evaluator in Runs, `done` and the gate. A base record never satisfies a required check by itself. Runs, the gate result (`baselineFailures`, also when allowed) and the briefing show such a step as “fails as on base”. Tests: `test/pipeline-baseline.test.ts`.
- **Only the owner reads its replies**: session id plus harness must match.
- **Loopback only.** The service binds 127.0.0.1 and checks the Host header (against DNS rebinding). Writes require `application/json`; a supplied browser `Origin` must use an allowed loopback host and port. No-Origin local CLI/server clients are accepted. Session matching is routing isolation, not authentication against other local processes; remote/reverse-proxy use is not supported.
- **Only explicit attachments.** Evidence is copied from paths the agent names, by type allowlist and size limit, never dotfiles. It is served with a sandbox CSP. An image you paste or drop is sent as base64 JSON (so the write guards above hold), taken only when its bytes are PNG, JPEG, GIF or WebP and it is at most 10 MB, stored under a random id in `uploads/` in the data directory and served the same way. A message or an answer names it by id; the agent is given its absolute path (`Image: /…`), never its bytes, since the text may be typed into a terminal. The preview check fetches only that item's own http(s) URLs. Pages are http(s) only and framed sandboxed; a page on the office's own origin gets no same-origin rights. The office's own app (any page it serves except `/files`, `/uploads` and `/api`, under any loopback name for its port) is never framed, since it would stay blank without those rights: the walkthrough shows a card with an Open in a new tab button, the page check says `own`, and the submit response carries a `warning` the CLI prints.
- **State lives outside worktrees** (`~/.review-inbox`, or `INBOX_DATA_DIR`), so branch switches and worktree deletion never lose it. An inbox repository grouping (`Project`) is a repository's git common dir, so all its worktrees share that grouping. An office project is a non-standing `Team` with its own worktree; an adapter project key is a separate URL namespace.

Correctness coverage: `test/inbox.test.ts` (revisions/staleness/owner/evidence), `test/typed-replies.test.ts` (pane ownership/restart), `test/http-contract.test.ts` (guards/methods/validation), `test/api-replay.test.ts` (scoped ids/atomic work), `test/autoapprove.test.ts` (inbox-only automatic answers), `test/qa-answers.test.ts` (the QA agent's answers and manual-mode predictions), `test/qa-agent.test.ts` (starting, replacing and closing the office's QA agent), and `test/pages.test.ts`/`uploads.test.ts` (framing/images).

## The office

The office is a second view of the same state, not a second system. It adds two things the inbox did not keep:

- **Agent identity** is harness plus checkout (`pi:/work/garden-notes-builder`), not the session, plus herdr's name for an agent herdr knows by one (`claude:/work/garden-notes@tests`), so a first mate's crew sharing its checkout stay apart. A lane restarted in its worktree is the same person with the same name, face and desk. The face is derived from the identity alone, so it never needs storing.
- **Projects and standing teams** (`teams`, `world_agents`; "team" in the code): a name, and exactly one lead once anyone is on it (the service appoints one: someone running, there longest, never someone in one of its other worktrees, below). A **project** is a worktree (`path`, `branch`): an agent placed nowhere whose checkout is a linked worktree is on that worktree's project, made on first sight and named after the folder. Its lead is the first mate, briefed to plan, start crew in herdr and supervise rather than write code. A **standing** team (Mission Control) has no worktree and keeps its members wherever they work. Offline, a standing team's members and a project's lead keep an empty desk; anyone else who stops running leaves. So does a standing team's offline member while another agent runs in the same checkout (matched on the checkout's top, not the raw cwd, and whether or not that agent is on the team): the new one replaced them, as when a Pi agent is swapped for Claude Code. A standing team's offline lead leaves only for a replacement on its own team, since it often works in a main checkout other projects' agents run in; a project's offline lead stays while one of its own members runs beside it, as that one may take its place. The record is kept and only its placement goes, so what it said keeps its sender, and if it led, the next lead is appointed as usual.
- **A team's other worktrees** (`team_worktrees`, `Team.worktrees`; its lanes): a project or standing team can own further linked worktrees of its repository, such as Mission Control's crew checkouts (`garden-notes-builder`, `garden-notes-reviewer`, `garden-notes-tests`). A worktree has at most one owner, as a project's own or as someone's lane. An agent placed nowhere who works in a lane is on its team as a **member**, and the office never appoints someone in a lane lead (you can); no project is ever made for a worktree a team owns. You add one on the team's Edit form (an existing worktree of the same repository, never the main checkout; another project's own worktree is refused with the advice to merge that project instead) and remove one there; removing only lets the record go, never the folder. A lane whose folder has gone is let go the same way. **Merge into…** folds a project into another team: its worktree and lanes become the target's lanes, its agents join the target as members, what was said to it and the work it handed over or was handed follow, and teams that handed work to it hand it to the target; then it is forgotten; its pipeline runs stay, archived under its own name and listed in the target's Runs, never the target's to deliver. Unlike finishing, nothing on disk or in herdr is touched: no worktree, branch, pane or process. It is refused while work waits for the project's review, and for a standing team that owns lanes (they would be left without a team): remove or move them first. Nothing is migrated automatically; a project made for a crew worktree before this is merged by hand.
- **Crew started elsewhere** (`pane_teams`; `inbox pane --cwd DIR`): when someone on a team opens a pane with `inbox pane`, the CLI tells the service (`POST /api/agent/pane`: the caller's session and the new pane id) and the service keeps the pair in the database. An agent that first runs in that pane and is placed nowhere joins that team as a **member**, never its lead, even in a checkout the team does not own (such as another repository's main checkout). This comes after the worktree rules: an agent in a project's own worktree or one of its lanes stays where those put it, and the checkout becomes neither a lane nor a project. A caller on no team records nothing. A record goes once an agent runs in its pane (placed or not), or a day after the pane was opened; a member you later move is not put back.

**Starting and finishing a project** go through herdr, which owns worktrees and panes. The repository is one someone already works in, another main checkout directly beside one of those (a one-level scan of the same parent folders, cached a few seconds, never a deep walk; the home folder is not scanned, and linked worktrees are skipped; known repositories are listed first), or any main checkout named by its path. A folder name with a space is fine: paths reach git and herdr as arguments, never through a shell, and the brief quotes them. The lead's start waits until the new pane shows its shell prompt, since herdr types the command at once and a shell still loading drops all but the first kilobyte. Starting makes the worktree beside the main checkout, on a new branch from the main checkout's branch, and starts the crew tree's current lead choice (Claude Code or Pi, subject to its mode and usage pause) there as first mate. The brief is appended to its system prompt. For Claude Code the inbox hook is added for that session only with `--settings`, pointing at this service; nothing is written to anyone's settings, and it is left out when the Claude Code settings read there already run `inbox hook claude`, so a reply is never handed over by two hooks. Whoever runs in the pane it was started in (`lead_pane`) is the project's lead, whatever herdr calls it: herdr can lose the name it started the agent with, which makes a second record, so a lead record left offline is folded into the running one, which keeps its name and what was said to it. A lead who is running, such as one you picked, is left alone. For a project from before that, a running agent's panel offers to make it the lead and take the name of a lead record that never ran (the same fold). Someone nothing runs behind can be removed from the office: the record is kept but hidden, so what it said and handed over keeps its sender, its undelivered messages are dropped, and the team's longest-standing running member leads next. It is refused while the agent runs, and running again brings it back. A folder-trust question at start is left for you to answer in herdr. Finishing refuses while work waits for the team's review or anyone there is working. **It refuses before closing anything while work has not landed** (`test/finish-unlanded.test.ts`): anything `git status` shows (removing the worktree would lose it), or commits checked out there that the project's integration branch lacks. That branch is `integrationBranch` from orchestrator.json, read as `origin/<branch>` when that exists and otherwise the local branch (no fetch: it is whatever was last fetched), or the main checkout's branch when none is named. The refusal (409, `finish_uncommitted` or `finish_unlanded`) is an ordinary `from_office` message to the project's lead (or, without one, everyone working in the worktree) saying what has not landed and asking them to land it on that branch through the project's pipeline and tell the founder it is ready; it is sent once per attempt, and not again while an identical one is still queued or sending. The note names who was told, or says nobody is there. **Finish anyway** (`force`) skips only the unlanded-commit check, so nothing is lost: uncommitted changes always refuse. Then it closes every pane working in the worktree, removes it, and deletes the branch with `git branch -d` only when every commit has landed, so a branch with unlanded commits is kept (the note says how many commits the integration branch lacks). A project whose worktree has gone is forgotten. **No team going, and no checkout seen missing, deletes pipeline history**: its runs, evidence files and bindings are kept, archived and never authorizing ([PIPELINES](PIPELINES.md)). Finishing removes only the project's own worktree: its other worktrees are never removed, only let go, so whoever works in one is placed again like anyone in an unowned worktree.

Agents come from herdr (all of them, including those that never posted) and from inbox tasks, joined on the session.

**Agent names** are unique case-insensitively and come from a large first-name pool before any numeric fallback. Once unused names run out, an offline record on no team, not removed, with no current task or pane and unseen for at least three days may release its name: it gets a unique “(earlier)” suffix atomically, while history keeps its agent id. Existing names (including numbered ones) stay stable on registration and activity; pre-migration records get a three-day grace period. These office display names are distinct from herdr agent names and Pi `/name` session labels: renaming a session label does not rename the office identity, and historical senders remain durable agent ids.

An agent writes its own one-off personal story with `inbox story "…"`: a childhood memory, a crisis it came through, what it loves or fears — not its job. Up to 800 characters of plain text on its identity record, shown quietly in its office panel and back to the agent in its `inbox team` briefing, inviting it to bring that person to its work. Introductions ask for 3–5 sentences in the first person, told plainly as its own life, separate from its task, with a few seeds (a place and decade, a parent's trade, an object, a happy moment, a fear) chosen deterministically from its agent id as a starting point, and name the office's overused themes to avoid; the office never generates stories or backfills existing agents. **A story that opens with a frame or disclaimer is refused with a 400 and not saved** (fictional, imagined, backstory, office story, a label, being an AI or a model, having no childhood; case and punctuation ignored; `test/story.test.ts`). A story records which prompt it answers (now the third): an agent whose story predates the current prompt is asked once, in its next delivered prompt, to retell it; its old story stays until it does, and retired agents keep theirs.

**Switching an agent to the other harness** (`switch.ts`, `agent_switches`; `inbox switch NAME [--to claude|pi] [--model M] [--effort E]`, `inbox switch --all-from pi`, and a Switch to … button on an agent's panel and its card on the board) is deterministic: no model is called, the agent writes its own handoff. The model comes from the crew tree: the other half of the pair the agent runs as (a lead's pair first, then the rules, then the fallback), else the standard stand-in for its model (Opus and GPT-6 Astra, Sonnet and GPT-6.1 Sol). Switching into a harness the founder's switch has turned off is refused, when asked and again before anything starts. The steps, each recorded with a sentence before the next begins: wait until the agent is free (30 minutes at most); ask it to write a handoff to `handoffs/switch/<name>-<time>-<switch-id>.md` in the data directory and wait for the file (10 minutes at most; it counts once the agent has finished its turn, or the file has been unchanged for 30 s); open a pane in its checkout beside its own (an agent not running skips the handoff and goes beside its lead, or in a workspace of its own); start the other harness there; close the old pane; take over; give the new session its brief (who it is now, and to read the handoff first). **Taking over** rewrites the agent's record to the new session's identity, so its id, name, team, role, messages and queued deliveries are simply still its own; a project's `lead_pane` moves with it, herdr's name for the old session passes to the new one, and the old identity is kept as removed, so the old session's inbox tasks do not bring back a stranger. Invariants, with tests: **the new session never shows in the office until it has taken over** (its pane is hidden, so it is never a stranger or a new project's lead), **the old pane is closed only once the new session runs**, **what waits for the agent is held from the start of the switch until the brief is typed**, and **a failure before the old pane closes closes the new pane and leaves the agent as it was**. A restart picks a switch up at its recorded step, but does not blindly repeat external effects: handoff path and effect intent are recorded before dispatch, pane creation carries a switch operation tag, and unknown opening/launch/brief outcomes pause visibly for recovery. A busy or trust-prompt replacement keeps its brief queued as a prerequisite, not an ordinary message; unconfirmed briefing keeps ordinary deliveries held. See `test/switch-boundaries.test.ts`. `--all-from` switches every running agent on that harness one at a time and lists those it cannot switch.

A repository can describe itself in **`orchestrator.json`** at its main checkout (the project adapter, [ORCHESTRATION.md](ORCHESTRATION.md)): its key in `/api/p/:project`, integration branch, preview address, comment kinds and anchor keys, checks, reviewers, landing commands and standing lanes. The service shows it on the repository in the world state and runs nothing from it, with one deliberate exception: a standing lane's own `attach` argv (below). It is read again when the file changes; a missing file is no adapter, and an invalid one is not used at all, with every problem listed (`adapterProblems`) rather than half-applied. Unknown top-level keys are listed and ignored; unknown nested fields are ignored without a warning. `GET /api/p/:project/queue` gives the project's own tools who works its queue: each of the adapter's `lanes` joined to an office agent (the one working in the lane's `worktree`, the one whose herdr name or Pi session name is exactly its `agent`, or both when both are given; with neither, the agent called by the lane's name), with its state, what it is doing, its branch and model. A Pi session's name is the one in its terminal title (`/name`); the Pi extension reports it, and the service keeps it per session in memory like the model, so a new session in the same checkout has not said it and a restarted office hears it again at the session's next turn or poll. A lane with `agent` never falls back to another agent, such as a Claude Code session in the same folder. A lane nobody runs in is listed `offline` with why. The comment counts are currently zero, held/carrying lists empty and paused false: comment intake, assignment, leases and landing are not implemented. Adapter commands/settings are descriptive, not automatically run or enforced. `inbox say <name>` also takes a lane's name, after office names and teams: it reaches the same agent, so a project's tools message their lanes by the names they already use. A name that is a lane in several projects means the sender's own.

**A standing lane that declares `attach`** (`standing.ts`, `GET /api/lanes`; `inbox lane`) is checked against the session its project registered for it, because a dispatcher whose standing session is gone stops a project while its team's lead is online and well. The office runs exactly that argv, without a shell, in the lane's checkout: `--status --json` when the lane is read (at most every 30 s per lane, no timer of its own), and `--recover --pane P --session S --json` only on the founder's explicit Recover, for someone running in that checkout. The command decides and does the attaching; its exit code and last line of JSON must agree, or the answer is treated as a transport error. A lane is `connected` only when the command says so **and** the office sees that exact session running in herdr in the lane's exact checkout, in the registered pane and on the lane's declared harness, so a stale registration (its pane closed, its companion still writing) or the same session id elsewhere never looks healthy. A transport error, a herdr the office cannot see or an ambiguous session is `unknown`, never `disconnected`: nothing is concluded from an outage. The lane joins the registered session's office agent rather than a herdr name, for the queue and for `inbox say <lane>`, so attaching needs no rename and the agent keeps its office id, name, team and messages. Recovery is one at a time per lane; its refusals (busy, refused, unavailable, failed, with the command's own log) are shown as the command said them; it is `attached` only once a status run started after the command returned (one already in flight is waited out and discarded) confirms that session in that pane. The office claims no more than that: the project's `progressAt` is shown as the session's last completed turn, not as proof of a board answer or pickup. Nothing is stored: after a restart the status is the truth, and repeating a recovery is the command's own idempotent retry. Recovery never changes a lead, a role or a message's recipients; changing lead stays the founder's choice. The cleanup guard (an agent marked as a lane's standing session in briefs and on the board; removing, switching it or finishing its team refused) relies on the lanes' cached status: before the first status, or after a failed one, it marks and refuses nothing, so it is not absolute protection. Run `inbox lane` before closing a pane in a project with standing lanes. Tests: `test/standing-lanes.test.ts`.

**Team status** is derived, never stored. A team is `blocked` when its lead is stuck, or when someone is stuck and nobody in it is still working; stuck means waiting at a prompt in herdr or waiting on a blocking inbox item. A crew member stuck while the lead works is the lead's to handle, so it does not reach you. Otherwise the team is `working`, `idle` or `offline`. The service announces a team through herdr's notifications once, on the change to blocked; on start it only takes note of how things stand.

**Messages** (`messages`, `message_deliveries`) are everything said in the office: your instruction to a team, an agent's message to another agent or a team, a handoff and a review verdict. They are kept like replies: never deleted, one delivery row per agent, and a client id so a retried request is not a second message. The agents a message goes to are fixed when it is given: a team's lead, or its crew (the running ones, else all) when the lead is the one speaking. A delivery is `queued` until its agent is free, then claimed as `sending` by a conditional update, so two reactions never type it twice, and ends `delivered` or `failed` (with herdr's reason). A new project's never-running lead with a `lead_pane` but no registered agent stays queued; herdr's definite “agent … is not an active named agent” refusal also returns the delivery to queued, preserving its original queue/Retry age and waiting for a presence event or the next poll rather than triggering its own immediate retry. These startup waits fail after three minutes from queue/Retry time if the pane still has no running agent or herdr still refuses it as inactive; registration while working or blocked keeps the usual wait-until-free rule, and established offline leads still wait to return. Only that pre-submission refusal is automatically retried: timeouts, closed panes and unconfirmed sends still fail. On service startup, any delivery left `sending` is marked `failed` with a warning that it may already have arrived and Retry may send it twice: a stopped sender must not reserve its agent forever, but an unconfirmed prompt is never automatically replayed or marked delivered. A failed delivery to a departed agent, or one whose pane closed during submission (including `PTY actor closed` and pane/agent not-found errors), says **left before it arrived**, without Retry. The service refuses retry for a missing/offline recipient or a closed-recipient failure; genuine transport failures to live recipients keep **not delivered** and Retry. Each agent takes one prompt at a time. What queued up while it was busy is typed as **one prompt**, oldest first, each message under who sent it and how long ago (`Alma, 42 min ago:`), headed by "N messages arrived while you were busy; later ones may supersede earlier ones. Reply once to what still matters." and closed by one footer, so an agent that was away an hour answers what still matters once instead of acknowledging each stale message in its own turn. A single message is typed exactly as it always was. The prompt is capped: the newest messages stay in full up to about 6000 characters, older ones shrink to a line of 160 characters (their `Image: /…` paths kept beside them), and at most 50 go in one prompt, the rest in the next. The deliveries in a prompt are claimed together and end `delivered` only when herdr sees the agent take the prompt up, or all `failed` together with herdr's reason (except the bounded startup requeue above); Retry puts one back in line, and those retried together are typed together again. The text of each is prefixed with who is asking, the team and the agent's part in it: a first mate is told to plan it, give it to its named crew or start more in herdr, supervise them and report the outcome; a standing team's lead to divide it among its crew. An agent **answers you** with `inbox say founder "…"`: a message marked `to_founder`, with no deliveries, so it is typed into no terminal and is not an inbox item. The office keeps your conversation with the agents apart from the rest of its talk (the latest 200), and an agent's panel shows it as a thread above the message box: what you said to it or to the team it leads, and its answers. Your messages tell the agent to answer in a sentence or two and to follow up the same way when the job is done or something new happens; decisions still go to `inbox decide`. No agent can be named "founder".

**Delegation is not founder approval.** An agent message names the sender's standing from office membership: your first mate only for your own team's lead, another team's first mate, a crew member or another office agent. This survives batch shortening and never turns a sender's claim into founder authority. Claude Code's terminal input distinguishes typed intent from pasted content; herdr's ordinary prompt pastes the entire wrapper. For Claude only, the office keeps one guarded `agent prompt` submission but inserts paste boundaries so a fixed office-authored framing line is typed and the entire message remains pasted. The framing asks it to handle the delivery under existing instructions and permissions, not to bypass any approval; payload terminal controls are refused before dispatch. Pi/Codex terminal transport, native reply integrations, settings and permission configuration are unchanged. Uptake still proves a turn started, not that the recipient accepted the task. Tests: `test/office-delegation.test.ts` (synthetic terminal events, not live-model certification).

**Office notices to the founder.** The office can put a line in the same founder conversation as agents' answers: `from_office` and `to_founder`, clearly labelled **The office**, associated with the agents concerned but with no terminal deliveries. It also attempts one herdr desktop notification per committed notice. Every reaction (including the 30-second poll) observes queued deliveries **after the guarded sender has had its chance**, using reconciled presence: if an agent is still idle or done and its oldest still-queued delivery has waited **more than ten minutes**, it reports “agent (project) is free but N messages have waited M minutes undelivered.” N is the whole queued count; M is the oldest wait in whole minutes, measured from the delivery's queue/Retry time. One durable latch per agent suppresses repeats until its queue drains; the latch and notice commit together, so a restart does not announce the same episode again. A long busy wait delivered normally at turn end is not an undelivered episode. This watchdog only observes: it never changes, claims or retries a delivery. Tests: `test/undelivered.test.ts`.

**A team with no lead online** (`leadwatch.ts`, `WorldTeam.stalled`). A queued delivery to an offline agent says so: its sender reads “Mission Control's lead (Alma) is offline” at once (in the `inbox say` answer, the founder's thread and the board), never “they seem busy”, which is kept for a running recipient. A team is **stalled** when its lead is offline (or it has none) and something has waited on it for **ten minutes or more**: a queued message to its lead (or, with no lead, to anyone on it; office notices do not count), work handed to it that is still in review, or an open pipeline step reported to its lead. Ages come from durable records (queue/Retry time, the work's or run's last update), so a restart sees the same stall. The board shows “<team> has no lead online; blocking: <teams/agents/you>” at its top and on the team's column, the office's team panel shows the same line, and a blocked agent's `inbox team` says the founder has been asked. The founder gets **one inbox decision per stalled team**, from the office's own session (`manual`, `office:lead-watch`, which is nobody in the office): “Make <member> lead” for each other member (running ones first) and “Wait for <lead>”, with no recommendation, so approve-all never picks a lead. **Nothing changes until the founder clicks**: there is no automatic acting lead. The decision is revised only when its wording changes (who waits, who is on the team), is withdrawn by itself once the team is no longer stalled (an answered one is resolved), and a later stall asks afresh as a new item; the item is the latch, so no table of its own. Choosing a member goes through the ordinary make-lead path (`updateAgent` with `role: "lead"`) and hands the old lead's queued, team-addressed messages to the new lead with their age (a message to the old lead by name stays theirs; a reply is acknowledged only after it is applied, and a member who has left fails it with Retry). “Wait” changes nothing and is not asked again in that stall. Tests: `test/leadwatch.test.ts`.

**Tell all leads** (`POST /api/world/all-leads/messages`) is one founder instruction with one fixed delivery per selected project or standing-team lead. Omit `leadIds` for all current leads, or send the checked lead ids; stale selections are refused before anything is stored. A required `clientId` makes retrying the entire broadcast idempotent, and the instruction and all deliveries are committed together. It uses the normal team instruction prompt and image paths. Offline leads remain queued and are listed in `queuedOffline`; teams without a lead are listed in `skippedTeams`. Both the office's Projects panel and the Projects board open the same checked-recipient composer. Each recipient's conversation and project thread mark it as an all-leads broadcast; their `inbox say founder` answers remain in those threads (not guessed to belong to a particular broadcast).

**Acknowledgment loops** are advisory, never a sending limit. Eight alternating, single-recipient agent messages under 300 characters within ten minutes queue one office notice to both agents to stop replying to acknowledgments and continue the work; every original message still goes through normally. The pair's episode and notice latch survive restarts. Ten minutes of silence, a handoff/review, a longer message, an image or a group exchange ends that episode; repeated senders break the alternating streak but do not rearm a notice. Founder and office traffic never count. A second trip by the same pair within 30 minutes sends one office-to-founder notice; further trips do not repeat it until more than 30 minutes pass between trips. The recurrence latch survives restarts.

**Work** (`work`) is finished work handed to another team to review: the team named, or the one the sender's team `handsTo`. It is `in_review` until that team (and only it) answers `accepted` or `changes_requested`; changes need notes. The verdict is a message back to whoever handed it over, and handing the same work over again starts its next round. The service decides nothing about the work itself: whether it is good is the reviewing agents' judgement.

**Usage** (`usage.ts`, `usage_readings`; `WorldState.usage`) is the founder's subscription use: a meter per limit (Claude's 5-hour window and week, Codex's week, and Codex's 5-hour window once a plan reports one) and each agent's and team's tokens this week. **No model is ever called for it, and the only account call is Codex's usage read (below)**: a meter is what the provider already said in the headers of a reply an agent was getting. Claude Code hands its plan's limits to its statusline command, so a Claude Code session the office starts gets `inbox statusline` in the same `--settings` as its hook (left out when the settings read there set a statusline of their own; nothing is written to anyone's settings), which posts them to `/api/agent/usage` and prints a short line. Pi's extension forwards Codex's `x-codex-*` headers from `after_provider_response`, and the newest codex CLI rollout's latest `rate_limits` are read lazily. Claude Code's own cache of its last `/usage` read (`cachedUsageUtilization` in `~/.claude.json`) is the fallback, shown with its age. One reading is kept per meter, and an older reading never replaces a newer one. A reading over 30 minutes old is `stale`; a window that has reset since its reading shows 0% and stale (the week keeps its weekday and hour; a 5-hour window's end is unknown until the next reading). Tokens (input, output and cache writes; cache reads left out) come from the session files each harness keeps: Claude Code's transcripts and their sub-agents' (a streamed reply is counted once), Pi's session files (its Codex replies count against Codex, its Anthropic ones against Claude), Codex's rollouts (a repeated count once). Token scans read a slice at a time in the background, from where each file was left. Token totals use that cache, but meter projection can still read local usage-limit caches and persist a newer observation; the office read path is not wholly file-free. A session belongs to the agent whose current session it is, or to the one agent of its harness in that folder, and to the team whose worktree (or other worktree) holds its folder. An agent's or team's `share` is an estimate: its part of a provider's weighted tokens this week (output weighs most, a cache read least) times that provider's weekly meter, so the parts add up to the meter; it is null when no reading belongs to this week. Use from other devices is not in the session files here, so on Claude it lands on whoever ran here.

**Optional integrations default off.** Set `INBOX_CODEX_ACCOUNT_POLLING=1`, `INBOX_PRESENCE_DISCOVERY=1` or `INBOX_BROWSER_CLEANUP=1` independently to enable authenticated account polling, continuous terminal discovery or machine/process control. Missing settings are off; `1/true` and `0/false` are accepted, invalid values fail startup. The established office's restart script explicitly enables all three. These are background-integration controls, not a sandbox: local harness session/usage files are still read, and explicit pane/project/switch operations (including switch resume) may call herdr.

**Codex's account read** (`codexaccount.ts`) is the one account call the office makes, **only when opted in**: every 5 minutes, and once at start, it reads the ChatGPT login in `~/.codex/auth.json` and asks `chatgpt.com/backend-api/wham/usage`, the endpoint the codex CLI's own `/usage` reads, so the Codex meter is right even when no Pi agent runs. It returns numbers (used percent, window length, reset time) and is not a model call. Its windows are told apart by their length and recorded as Codex readings through the same path, so a newer reading wins. `auth.json` is only read: the token is never refreshed (that rotates it and could log the founder out of Codex), written, logged or stored, and goes to that one host only (no redirect followed). An expired or refused token, or a failed call, is skipped quietly and the meter goes stale.

**The founder's rule near Claude's 5-hour limit**: while the crew guide's switch is Mix and Claude's 5-hour meter is at 90% or more (a high reading holds until its window resets, whatever its age, since use only grows until then; one with no known reset counts only while under 30 minutes old), the guide (`inbox crew`, a lead's `inbox team`, and the lead a new project starts with) treats Claude Code as switched off and gives each rule's Pi backup, saying why and until when. The founder's saved setting stays Mix, crew already running carry on, and switching an agent is not affected. On "Claude Code only" or "Pi only" it changes nothing. With no reading, nothing is paused. The mirror image: under Mix, when any Codex meter (the week, and the 5-hour window when a plan reports one, told apart by their window minutes, not by primary or secondary) is at 90% or more, the guide treats Pi as switched off and gives every Pi rule's Claude backup (and a new lead its Claude backup), saying why and until when. A high Codex reading holds the same way, with the last of the high meters deciding when. When both limits are high, Claude is kept (the founder's default, and its window ends sooner): Pi is paused, not Claude Code, and the founder is told once per Claude pause, and only under Mix (an office notice, latched in `usage_told`, checked on the service's 30-second tick).

**Activity** is what an agent is doing right now (its current tool, as one line) and its **helpers** (sub-agents). It comes from the harness: Claude Code through an HTTP hook (`/api/hooks/claude`: PreToolUse, SubagentStart/Stop, Stop), Pi through its extension (`/api/agent/events`). It is kept in memory only, because it describes the last minutes: a tool line fades after two minutes, a helper nobody hears from after thirty, and a finished turn clears both. Activity changes are broadcast but never make the service react, so they cannot trigger a delivery. The **model** an agent runs is reported the same way, for the session that reported it: Claude Code's from the hook input's `model` (SessionStart, through `inbox hook claude`) or its transcript's latest reply (read at each Stop, or when none is known yet), Pi's from `ctx.model` at session start, on `model_select` and at each turn's end. When a harness has not reported it (a Pi agent started before the extension did, Codex, Claude Code without the hooks), the service reads the session file the harness itself keeps: Pi's session file (its latest `model_change` or assistant message), Codex's rollout (its latest `turn_context`), Claude Code's transcript. That read is lazy, when the office is drawn, and repeated only once the file has grown and at most every ten seconds; what the harness reports wins over it. Every path names the model the same way, specific rather than a family ("Opus 5.5", "GPT-6"), with the raw id beside it; the office shows nothing when no model is known.

**Effort** is session state, separate from a requested change. A live integration advertises `capabilities.changeEffort` and its model's accepted levels; the office's agent panel shows only those choices and the Projects board shows the reported level. Pi polls `/api/agent/effort`, waits until idle, calls its real `setThinkingLevel` API (session-only, never the configured default), and reports `getThinkingLevel` plus the request id. `thinking_level_select` also reports changes made in Pi itself. Requests belong to the exact harness/session, are applied once per integration instance, and stay pending until acknowledged; a different/clamped level or no confirmation within 30 seconds is a visible failure. The reported level is never optimistically changed. Current limitation: effort requests/results, like effort reports, are in memory; a service restart loses an outstanding request rather than exposing an interrupted result. Do not mistake that control for a durable receipt. The installed Claude Code's `/effort` command accepts low/medium/high/xhigh/max but persists all except max as that model's default in user settings. It is deliberately **not offered**: no verified local session-only control exists, and restoring shared defaults afterwards would race other sessions. Its capability carries the explanation; the UI never branches on its vendor. No effort control types terminal input or starts a model turn.

**Unpresented work.** Each submitted or revised milestone and try records the assigned project's worktree HEAD on the item and its revision; the latest submission is the project's presented point, whoever on the crew posted it. Decisions also capture HEAD to recognise a pending question, but do not advance that point. Every minute, git counts commits reachable from the worktree HEAD but not from either the main checkout's HEAD (its base branch) or the presented point. Counts are cached by those three commits; neither a merge into base nor a new presentation needs a new worktree commit to clear the count. Projects show a neutral “2 commits not shown to you yet” on the board and in the office panel. Standing teams are excluded.

When a lead has been continuously idle or done for five minutes, with neither the lead waiting on the founder nor its team blocked, unpresented commits cause an ordinary `from_office` message to that lead, delivered by the existing guarded terminal path. It asks for a milestone now (screenshots, pages or video, even before the whole project is done), or a one-line explanation with `inbox say founder`. No reminder is sent with an unanswered item at current HEAD (including snoozed items). The per-project 30-minute cooldown and last reminded HEAD survive restarts; a say-to-founder by the reminded lead after that reminder suppresses it for that HEAD until a new commit. A restart begins a fresh five-minute idle observation, never guesses that an offline lead is free. This detects unshown commits, not whether the work is good or finished; no model is involved.

**A whole team idle.** Independently of commits, a project whose lead and every crew member have been continuously idle or done for five minutes gets an office reminder to present finished work, ask the founder for what is missing (`inbox decide`, with options or an open question), or say what happens next. Nobody may be at a prompt, blocked, offline, unknown or waiting on the founder. Any unanswered project item (at any HEAD, including snoozed and legacy items) suppresses it, as does the lead saying anything to the founder since that idle episode began. It is sent only once until someone on the team is observed working again: a prompt, changed crew or service restart does not rearm it. The latch, explanation cutoff and last reminder time survive restarts; the five-minute observation starts afresh. Both reminder rules share a 30-minute per-project cooldown and produce one combined office message when both apply. The unpresented-commit rule still operates independently, including while crew work.

**Headless browsers**, when `INBOX_BROWSER_CLEANUP=1`, are watched outside herdr and the inbox, because an agent's forgotten browser (a script's, or a dev server's probe) can take the machine's CPU with nobody noticing. Every 15 s the service reads `ps` and finds browsers a program started: a headless build, `--headless`, or a Playwright or Puppeteer profile; a browser you use yourself matches none of these. Each main process is grouped with everything under it (pages, GPU, network) and summed. It belongs to the project whose worktree (or the agent whose folder) holds the working folder of the nearest process in its lineage, read once per process with one `lsof` for all new ones (`/proc` on Linux), else to nobody. A browser is **forgotten**, and closed by the office itself, when its starter has exited (its parent is launchd or init, or gone from the list) for a minute while its project has had no busy agent for that minute (a browser of no project: while it uses under 5% CPU), or when it is over 10 minutes old and its owner has done nothing with it for 10 minutes: its project has had no busy agent (counted from when the office saw it), or, for a browser of no project, it has used under 5% CPU. A browser keeps the project it had while its starter lived. One whose project has a busy agent is never forgotten, orphan or not: it may be mid-screenshot, or detached on purpose and reused over a debugging port. The office sends SIGTERM to the main process and, if that same process (same pid, parent and command, read from `ps` again) is still there 10 s later, SIGKILL to it alone; it then tells the project's lead once, as a message from the office (`from_office`: no sender, typed as "[From the office]", never shown as yours; a project hears at most every 15 minutes), and counts it for a quiet "Closed N forgotten browsers today" on the Projects board (in memory, since the service started). One that cannot be signalled, or outlives SIGKILL for 45 s, is listed with the warning for the founder instead. A browser that may still be in use is only a warning, shown when together they use over 150% CPU for a minute or more than five run; it is kept in memory only, and Close is the founder's click. Invariants hold, with tests: **only forgotten headless browsers are closed automatically, nothing else, ever**, and **only a listed headless browser's main process is ever signalled** (Close and the automatic close alike): the process list is read again, any pid that is not a headless browser's main process in it is refused, and a browser of a working project is not closed automatically. A flagged (hot) browser for three minutes is told to its project's lead once, as above.

The office draws all of this from the same state, without storing anything of its own. **Building is the only office**: no layout selector or stored layout choice is used, including an old `ring` value. Teams occupy bays round an open hall, and people follow its rectangular walkway between rooms, clear of furniture and planted beds. A message that arrives while you watch becomes a **visit**: the sender walks to the first recipient, says it in a speech bubble (carrying a folder for a handoff) and walks back. Your own instructions are bubbles over the agents that hear them. A blocked team is standing state rather than an event: its running lead stands on the garden's clearing, facing you, for as long as the team is blocked, and a card offers what fits (the answer card for a decision; for someone at a prompt, who it is, a message asking the lead to handle it, or their panel). The office offers no allow or deny, since it cannot see the prompt. Sending the lead back holds until who is stuck, or why, changes; it is kept in the page only. The `handsTo` links are arrows between team bays, along the lane just inside the hall's walkway. The **board** (`#/teams`) shows the same projects, work and messages as columns and lists.

The hall's middle is an indoor garden, with no founder desk or desk-return camera control: agents on no project spend their idle time there, on benches or strolling round a walk, and keep to its paths. At the garden's front is a paved clearing where you stand: a lead who comes to you stands there facing you, and agents waiting for you gather beside the way in, in order, without ropes. The garden is planted thick (trees of several kinds, shrubs, ferns, grasses and flowers, a pond with reeds, lilies and ducks), but nothing grows on a path, the clearing, a bench or the gravel beside one, and nothing tall stands between the opening view and the clearing; the tests hold it to that.

The building's two glass rooms are **creative review rooms**: a generic architecture whiteboard, a table with chairs and sticky notes, and a tabletop projector. A running review helper (a reported type/definition name containing `review`) sends its parent there, as does office work `in_review` assigned to that reviewer. Pending handoffs have no `reviewerId` until their verdict, so their receiving team's lead owns the review meanwhile. One agent reserves each room, existing occupants stay put, overflow stays at its station, and the agent walks back when its reviews finish. The founder's queue takes precedence.

A helper's Read/View activity can carry `helperId`; Claude's hook preserves it rather than discarding that helper's tools. A reported safe review-helper excerpt takes precedence; a parent's unrelated reads or shell output never become helper excerpts. When none is available, the office **picks source code itself** for the active review: from the handing-over agent/team's checkout for review work, or the parent checkout for a review helper. `review-fallback.ts` asynchronously enumerates local git candidates (no network fetch), preferring changed files before other tracked files, and rotates a deterministic selection every 20 seconds. Candidate lists refresh at most once per checkout/minute; a cold cache shows the idle slide without blocking the snapshot on git. This is derived presentation, never invented tool/helper activity or a request to an agent.

Both routes use `review-excerpt.ts`: canonical checkout confinement, no dot/private files, a source-extension allowlist, at most 128 KB, and binary/credential-looking content withheld. At most twelve short lines reach the UI. Safe bytes are re-read even within a cached candidate-list lifetime, so a newly credential-bearing file is withheld. A refused helper read clears its reported excerpt; stop, idle and helper expiry remove helper state, but active review work can still supply a fallback. The UI paints only supplied safe lines, otherwise a quiet idle slide. Tests: `test/review-fallback.test.ts`, `test/review-fallback.browser.mjs`; no vendor logic or model call is added.

The queue on the clearing is `needsYou` from the inbox, one place per agent. The office never shows an agent's terminal: you read what they are doing and what was said, and a message to one agent goes through the same deliveries as everything else. herdr's own errors reach the UI as one line.

## Exact-SHA repair waiver

The founder's one sanctioned way to deliver a commit without a pipeline run (`src/server/pipelines/waiver.ts`, migration 11, `test/pipeline-waiver.test.ts`). It exists for repairs, like a broken guard, that a blocked team cannot put through a run. Only the founder's attention guards it, so its rules are narrow:

- **Who asks.** The team's lead, or any member while the team has no lead online (otherwise 403 `pipeline_lead_required`): `inbox pipeline waiver --repo R --ref dev --candidate SHA --reason "…"`. The candidate must be a commit id (not a ref name) that builds on the branch's current position. A rewind or rewrite, a no-op and `main`/`master` are refused. A retry with the same client id returns the same waiver, and a second request for the same commit, branch and base while one is waiting returns that one: one question, one item.
- **What the founder sees.** One blocking inbox decision from the office ("Repair waivers", grouped under the repository), naming the requester and their role, the repository, the branch, the full commit id, the reason, the complete `git diff --stat` and the diff itself against where the branch points now (shown up to 40,000 characters; `diffSha256` covers the whole diff). It has two options, **Allow this commit once** and **Refuse**, and no recommendation.
- **Only the founder's explicit choice counts.** Approve all never answers it (the waiver row commits with the item, so automation sees it from the first moment), and an automatic answer that reached it anyway grants nothing. A message is conversation: it never grants, refuses or revokes. A message before the founder decides puts the request back in Needs you as a new revision. Once decided, the item is resolved and takes no further answers. Revoking a grant is not built; it lapses on its own.
- **What a grant allows.** Exactly that commit, to exactly that branch, in exactly that repository (its Git common dir, so any of its worktrees), for a `push`, `land` or `publish`, never a PR or merge. It allows only while the branch still points to the base the diff was taken against, and only until 24 hours after the founder's Allow. An unanswered request lapses 24 hours after it was made, and its item is withdrawn.
- **Single use.** The first allowed gate call consumes the waiver (`used`). That same delivery's later boundaries (a tool preflight followed by Git's pre-push, or land followed by publish) are allowed for 15 minutes while the branch has still not moved. Once the branch has moved, including by that delivery itself, nothing is allowed. A refusal never consumes it.
- **Where it is checked.** A protected delivery that names **no** pipeline run (`inbox pipeline gate` without `--run`, which is what the installed hooks run when no `INBOX_PIPELINE_RUN` is given) asks the waiver gate, `POST /api/agent/pipeline/waiver/gate`. A delivery that names a run is judged by the run gate alone, and a waiver never repairs a run's refusal.
- **Record.** Rows are never deleted. Every step is an event: `pipeline.waiver.requested`, `.granted`, `.refused`, `.used`, `.allowed` (a follow-up boundary), `.expired` and `.gate_refused` with its reasons. Runs lists the repository's waivers as waiting for you, granted, used, expired or refused.

**Data contract for other enforcement points** (such as a GitHub ruleset bot). The `pipeline_waivers` table, also served as `PipelineWaiver` in `src/shared/waiver.ts` by `GET /api/world/teams/:id/pipeline/waivers`:

| Field | Meaning |
|---|---|
| `id` | waiver id |
| `repoCommon`, `repoRoot` | the repository's Git common dir (its identity) and main checkout |
| `ref` | short branch name, e.g. `dev` |
| `targetRef` | the ref whose position was shown: `refs/remotes/origin/<ref>` when it existed, else `refs/heads/<ref>` |
| `candidate` | full commit id that may be delivered |
| `base` | `targetRef`'s commit when the diff was taken; the waiver is usable only while the branch is still here |
| `diffStat`, `diffSha256` | what the founder saw: the stat, and the sha256 of the whole diff `base..candidate` |
| `reason`, `requestedBy`, `requestedTeamId`, `requesterRole` (`lead`/`crew`), `requestedAt` | the request |
| `state` | `requested` → `granted` or `refused`; `granted` → `used` or `expired`; `requested` → `expired` |
| `decidedAt`, `decidedReply` | when the founder chose, and the reply id |
| `expiresAt` | an unanswered request lapses at this time; after Allow, the grant lapses at this time (24 h after the choice) |
| `usedAt`, `usedBy`, `usedUntil` | the first allowed gate call, and the end of that delivery's follow-up window |

Another enforcement point should honour a waiver exactly when `state` is `granted` (or `used` with now before `usedUntil`), now is before `expiresAt`, the update targets `ref` in this repository with new value `candidate`, and the remote branch's old value is `base`. It must never widen that: not another commit, not a descendant, and not a force update. Recording the use belongs to the office (`POST /api/agent/pipeline/waiver/gate`), so a second enforcement point sees `used` and stops once the branch has moved.

## Lane delivery outside runs

First-mate-only delivery is a rule **inside** office pipeline runs. Lanes named in `pipelineHooks.laneDelivery.lanes` deliver their own fixes outside runs, and the installed hooks decide that class from the **candidate checkout**, never from a missing run variable. A commit checked out in exactly one declared lane's worktree, with no run named and no change to a policy path, is allowed without the office. Everything else asks the office: a named run goes to the run gate, otherwise the waiver gate. So a crew member who leaves out the run variable is still refused. The main checkout is never a lane, and a lane checkout never holds a run (`pipeline_lane_checkout`). Lane fixes to the adapter, the guard files or declared `policyPaths` need a founder waiver. A lane landing is recorded under the Git common dir, so the main checkout's push of exactly that commit is the lane's publication. Like every local guard this is advisory: it stops mistakes, not an agent that deliberately works from a lane's checkout. Details: [PIPELINES.md](PIPELINES.md#lane-delivery-outside-runs).

## Codex

Codex posts through the CLI and receives by **pull** today. Two routes could make it boundary or live; each needs a check against the installed Codex before building on it:
1. **Codex hooks** (a Stop-style hook). This would reuse the Claude hook's shape.
2. **`codex queue --thread <id>`** to push a follow-up into a running thread. This would give live delivery without a terminal.

Also unconfirmed: that Codex exports the thread id to tool shells as `CODEX_THREAD_ID`. Until that is checked, run the CLI with `--harness codex --session <thread id>` or inside herdr, which resolves the pane.

## Verification boundary

`npm run demo` is an isolated fictional example, not real-harness certification. `test/http-contract.test.ts`, `test/agent-client.test.ts`, `test/pi-delivery.test.ts`, `test/typed-replies.test.ts` and switch recovery tests cover the protocol and failure boundaries with isolated fixtures. Pi delivery confirms an actual user-message receipt rather than treating a fire-and-forget call as success. These checks do not establish compatibility with arbitrary Pi/Claude/Codex/herdr versions; verify the installed integration and one real submit → answer → receipt → ack round trip before relying on it. Browser scripts are separate from `npm test` and must run only against scratch services.

## Deliberately not here

- A reasoning agent that triages or summarises. The agents already hold the context. The one exception is QA answers, the founder's opt-in: an ordinary office agent, not part of the service.
- Live voice conversation (a later layer).
- Model API calls of any kind.
