# Design

The Review Inbox is for projects that run for weeks, where agents need your judgement more often than they need your typing. Mission-control tools show you terminals. This one shows only the moments that need you, with the evidence to decide from, and routes your answer back to the conversation that asked.

## What the UI talks to

**The UI talks only to the local service.** It uses HTTP for reads and actions and one SSE stream (`/api/events`) that says "something changed". It never talks to an agent, a harness or herdr.

This keeps the UI vendor-neutral. The service keeps three things per task:

| Kept | Why |
|---|---|
| **Harness** (`pi`, `claude`, `codex`, `manual`) | shown as a label; it picks the setup hint, never a code path in the UI |
| **Stable session id** (Pi: session file; Claude: `CLAUDE_CODE_SESSION_ID`; Codex: `CODEX_THREAD_ID`; else the herdr pane resolved to its agent session) | the reply's address. It survives restarts, and it is the same id herdr reports, so presence joins on it |

A Pi session's id is the **absolute path of its `.jsonl` file** (as the extension registers it and herdr reports it), never the id in the file's header. Anything submitting on a Pi agent's behalf, such as a daemon using `inbox --harness pi --session <path>`, must use that path: a reply is handed only to the session id it was submitted under, so the header id names a session nobody listens to.
| **Capabilities**, learned from behaviour | what the UI branches on |

The reply route is **learned, not configured**:
- **live**: an integration has polled with `mode: "live"` in the last 15 s (the Pi extension). The reply appears in the running session within seconds.
- **boundary**: a hook has called (Claude Code Stop / UserPromptSubmit / SessionStart). The reply lands at the next turn boundary.
- **pull**: neither has happened. The reply waits for `inbox replies`, unless the session runs in a herdr pane (below).

A session without a live integration that sits idle would never see an answer: a hook hands replies over only at a turn boundary, and an idle agent reaches none until someone prompts it. So when herdr shows such a session (pull or boundary) idle or done, the office **types the reply into its pane**, in the words the hook uses. It is claimed before typing, so it is typed once, and while it is typed no hook or pull is handed it (the prompt itself fires Claude Code's UserPromptSubmit). It is `delivered` only once herdr sees the agent take the prompt up; if herdr cannot type it, it fails like any other delivery, back in Needs you with Retry. A reply a hook or `inbox replies` already collected is never typed.

The UI shows the route as one sentence under the answer area, so you know what "sent" means before you send.

**herdr is a presence provider, not a bus.** The service reads `herdr agent list` for status (working / idle / blocked / done) again whenever herdr's socket reports a status change or a pane coming or going, with polling as the fallback. It uses `herdr agent focus` for **Open conversation**. An integration or a hook is the first route for a reply, since it is acknowledged by the session itself and ties the inbox to no multiplexer. When herdr is missing, presence shows "unknown" and nothing else changes.

Two things are typed into a pane instead: a reply to an idle session nothing else would hand it to (above), and a **message in the office** (below): your instruction to a team, or one agent to another. Neither can wait for a turn boundary an idle agent never reaches. Both are typed with `herdr agent prompt`, one prompt per agent at a time (your answer to something it asked first, as its own prompt, then the messages: see Messages below), under three guards: it is sent only when herdr reports the agent idle or done, herdr itself refuses an agent that is asking something, and herdr must see the agent start working within seconds for the delivery to count.

A reported `working` status is not trusted forever. The service samples the visible pane (at most once per 30 seconds) only for queued recipients or agents observed working for three minutes. Three minutes of unchanged sampled content makes that presence `idle`, both for the office and the same guarded, batched delivery path. Changed output, an unreadable pane, a session change or a new prompt clears that evidence; elapsed working time alone never makes an agent free. With no queued delivery, observation starts after three minutes working, so the earliest stale verdict is six minutes. A founder message still queued after ten minutes shows its waiting age in the thread and is logged once per queued attempt.

## The three item types

| Type | You get | Primary actions |
|---|---|---|
| **Decide** | the question as the title, what the agent needs and what happens if nobody answers, 2+ options with consequences, the agent's pick and why, screenshots | pick an option (plus an optional note) |
| **Decide, open question** | the same with no options: a question that has no fixed answers | write the answer (text required; the button says **Answer**) |
| **Try it** | what to check, a live preview or a walkthrough of pages (each checked for reachability and framing, shown at desktop or phone width), setup notes | open it, then **Approve** (an optional note) or **Needs changes** (a note saying what, required) |
| **Review milestone** | what was finished, evidence at the exact revision | Accept, or Request changes (text required) |

A decision has two or more options, or none. With none it is an **open question**: the answer is words (`answer`, worded to the agent as "Answer: …", and an empty one is refused), so a held question with no structured choices needs no invented ones. Exactly one option is refused, since it is not a choice, and a recommendation needs options, since it picks one. Revising by key works the same for both, and adding or removing the options makes a new revision that turns an answer written for the old one stale.

A try-it request is answered with the milestone's two actions, `accept` and `request_changes`, worded to the agent as "Approved" and "Needs changes". Approving does not update the task's last accepted milestone, since a try is not one. `tried`, what a try was answered with before, is no longer accepted; the replies that carry it stay in the database and the conversation reads "Tried it".

**Discuss** (free text to the owning agent) and **Later** (snooze 1 h / 3 h / tomorrow, or mark handled) are on every type. A choice never stops you writing more.

## Layout

- **Left rail**: Needs you / Working / Parked with counts; projects with waiting counts and pins; herdr status; key hints.
- **Queue** (Needs you): filter chips by type with counts. The sort is stated on screen: pinned projects, then items an agent is blocked on, then the longest waiting. `n` opens the next item, `j`/`k` move. Each card shows type, task · project, age, a thumbnail, owner and harness, and whether the agent is waiting.
- **Detail**:
  - The header shows owner, harness, live status and Open conversation.
  - Tabs appear only when they have content: Context (with the task brief), Screenshots (older revisions dimmed), Live preview (or Pages, a walkthrough: one live frame at a time with what to look at, Previous/Next and ← →, opened first when there are several; a page that is down or refuses framing says so with an open-in-tab link), Conversation (your replies with their delivery state and a Retry).
  - The answer area is pinned at the bottom.
- **Working / Parked**: one card per task with its brief (objective, latest decision, last accepted milestone, doing now, next milestone), its open items and Park / Open conversation. Parking hides a task's items from Needs you; it does not pause the agent.

The **task brief** is project memory for you rather than for the model. It is edited by hand, and updated when you pick an option or accept a milestone.

## Correctness rules

- **Stable ids.** An item is `(task, key)`. Resubmitting the same key with identical content changes nothing. Changed content becomes a new revision. For a milestone or try in a project worktree, its captured HEAD is part of the evidence: presenting a new commit with the same prose makes a new revision.
- **Stale answers are visible.** A reply carries the revision it answered. Answering an out-of-date revision is refused (409). A queued reply that a new revision overtakes turns `stale`, and the conversation says so.
- **Delivery is acknowledged.** A reply is `queued` until an integration claims it, and `delivered` only after that integration acks it, or, for a reply the office types into a pane, after herdr sees the agent take it up. A reply is typed at most once and never both typed and handed over. If a claim has no ack after 30 s, the reply is shown as *uncertain*. A failed delivery returns the item to Needs you with Retry. Each send carries a client-made id, so a retried request never becomes a second answer.
- **Only the owner reads its replies**: session id plus harness must match.
- **Loopback only.** The service binds 127.0.0.1 and checks the Host header (against DNS rebinding). Writes require `application/json` and a same-origin `Origin`.
- **Only explicit attachments.** Evidence is copied from paths the agent names, by type allowlist and size limit, never dotfiles. It is served with a sandbox CSP. An image you paste or drop is sent as base64 JSON (so the write guards above hold), taken only when its bytes are PNG, JPEG, GIF or WebP and it is at most 10 MB, stored under a random id in `uploads/` in the data directory and served the same way. A message or an answer names it by id; the agent is given its absolute path (`Image: /…`), never its bytes, since the text may be typed into a terminal. The preview check fetches only that item's own http(s) URLs. Pages are http(s) only and framed sandboxed; a page on the office's own origin gets no same-origin rights. The office's own app (any page it serves except `/files`, `/uploads` and `/api`, under any loopback name for its port) is never framed, since it would stay blank without those rights: the walkthrough shows a card with an Open in a new tab button, the page check says `own`, and the submit response carries a `warning` the CLI prints.
- **State lives outside worktrees** (`~/.review-inbox`), so branch switches and worktree deletion never lose it. A project is a repository's git common dir, so all its worktrees are one project.

## The office

The office is a second view of the same state, not a second system. It adds two things the inbox did not keep:

- **Agent identity** is harness plus checkout (`pi:/…/space-shuttle-einstein`), not the session, plus herdr's name for an agent herdr knows by one (`claude:/…/space-shuttle-atoms@tests`), so a first mate's crew sharing its checkout stay apart. A lane restarted in its worktree is the same person with the same name, face and desk. The face is derived from the identity alone, so it never needs storing.
- **Projects and standing teams** (`teams`, `world_agents`; "team" in the code): a name, and exactly one lead once anyone is on it (the service appoints one: someone running, there longest, never someone in one of its other worktrees, below). A **project** is a worktree (`path`, `branch`): an agent placed nowhere whose checkout is a linked worktree is on that worktree's project, made on first sight and named after the folder. Its lead is the first mate, briefed to plan, start crew in herdr and supervise rather than write code. A **standing** team (Mission Control) has no worktree and keeps its members wherever they work. Offline, a standing team's members and a project's lead keep an empty desk; anyone else who stops running leaves. So does a standing team's offline member while another agent runs in the same checkout (matched on the checkout's top, not the raw cwd, and whether or not that agent is on the team): the new one replaced them, as when a Pi agent is swapped for Claude Code. A standing team's offline lead leaves only for a replacement on its own team, since it often works in a main checkout other projects' agents run in; a project's offline lead stays while one of its own members runs beside it, as that one may take its place. The record is kept and only its placement goes, so what it said keeps its sender, and if it led, the next lead is appointed as usual.
- **A team's other worktrees** (`team_worktrees`, `Team.worktrees`; its lanes): a project or standing team can own further linked worktrees of its repository, such as Mission Control's crew checkouts (`space-shuttle-galilei`, `-heisenberg`, `-einstein`). A worktree has at most one owner, as a project's own or as someone's lane. An agent placed nowhere who works in a lane is on its team as a **member**, and the office never appoints someone in a lane lead (you can); no project is ever made for a worktree a team owns. You add one on the team's Edit form (an existing worktree of the same repository, never the main checkout; another project's own worktree is refused with the advice to merge that project instead) and remove one there; removing only lets the record go, never the folder. A lane whose folder has gone is let go the same way. **Merge into…** folds a project into another team: its worktree and lanes become the target's lanes, its agents join the target as members, what was said to it and the work it handed over or was handed follow, and teams that handed work to it hand it to the target; then it is forgotten. Unlike finishing, nothing on disk or in herdr is touched: no worktree, branch, pane or process. It is refused while work waits for the project's review, and for a standing team that owns lanes (they would be left without a team): remove or move them first. Nothing is migrated automatically; a project made for a crew worktree before this is merged by hand.
- **Crew started elsewhere** (`pane_teams`; `inbox pane --cwd DIR`): when someone on a team opens a pane with `inbox pane`, the CLI tells the service (`POST /api/agent/pane`: the caller's session and the new pane id) and the service keeps the pair in the database. An agent that first runs in that pane and is placed nowhere joins that team as a **member**, never its lead, even in a checkout the team does not own (such as another repository's main checkout). This comes after the worktree rules: an agent in a project's own worktree or one of its lanes stays where those put it, and the checkout becomes neither a lane nor a project. A caller on no team records nothing. A record goes once an agent runs in its pane (placed or not), or a day after the pane was opened; a member you later move is not put back.

**Starting and finishing a project** go through herdr, which owns worktrees and panes. The repository is one someone already works in, another main checkout directly beside one of those (a one-level scan of the same parent folders, cached a few seconds, never a deep walk; the home folder is not scanned, and linked worktrees are skipped; known repositories are listed first), or any main checkout named by its path. A folder name with a space is fine: paths reach git and herdr as arguments, never through a shell, and the brief quotes them. The lead's start waits until the new pane shows its shell prompt, since herdr types the command at once and a shell still loading drops all but the first kilobyte. Starting makes the worktree beside the main checkout, on a new branch from the main checkout's branch, and starts Claude Code there as first mate (`--model opus --effort medium`, the brief appended to its system prompt, and the inbox hook added for that session only with `--settings`, pointing at this service; nothing is written to anyone's settings, and it is left out when the Claude Code settings read there already run `inbox hook claude`, so a reply is never handed over by two hooks). Whoever runs in the pane it was started in (`lead_pane`) is the project's lead, whatever herdr calls it: herdr can lose the name it started the agent with, which makes a second record, so a lead record left offline is folded into the running one, which keeps its name and what was said to it. A lead who is running, such as one you picked, is left alone. For a project from before that, a running agent's panel offers to make it the lead and take the name of a lead record that never ran (the same fold). Someone nothing runs behind can be removed from the office: the record is kept but hidden, so what it said and handed over keeps its sender, its undelivered messages are dropped, and the team's longest-standing running member leads next. It is refused while the agent runs, and running again brings it back. A folder-trust question at start is left for you to answer in herdr. Finishing refuses while work waits for the team's review, anyone there is working, or `git status` shows anything, since removing the worktree would lose it. Then it closes every pane working in the worktree, removes it, and deletes the branch with `git branch -d`, which keeps an unmerged branch (the note says how many commits the main checkout's branch lacks). A project whose worktree has gone is forgotten. Finishing removes only the project's own worktree: its other worktrees are never removed, only let go, so whoever works in one is placed again like anyone in an unowned worktree.

Agents come from herdr (all of them, including those that never posted) and from inbox tasks, joined on the session.

**Switching an agent to the other harness** (`switch.ts`, `agent_switches`; `inbox switch NAME [--to claude|pi] [--model M] [--effort E]`, `inbox switch --all-from pi`, and a Switch to … button on an agent's panel and its card on the board) is deterministic: no model is called, the agent writes its own handoff. The model comes from the crew tree: the other half of the pair the agent runs as (a lead's pair first, then the rules, then the fallback), else the standard stand-in for its model (Opus and GPT-6 Astra, Sonnet and GPT-6.1 Sol). Switching into a harness the founder's switch has turned off is refused, when asked and again before anything starts. The steps, each recorded with a sentence before the next begins: wait until the agent is free (30 minutes at most); ask it to write a handoff to `handoffs/switch/<name>-<time>.md` in the data directory and wait for the file (10 minutes at most; it counts once the agent has finished its turn, or the file has been unchanged for 30 s); open a pane in its checkout beside its own (an agent not running skips the handoff and goes beside its lead, or in a workspace of its own); start the other harness there; close the old pane; take over; give the new session its brief (who it is now, and to read the handoff first). **Taking over** rewrites the agent's record to the new session's identity, so its id, name, team, role, messages and queued deliveries are simply still its own; a project's `lead_pane` moves with it, herdr's name for the old session passes to the new one, and the old identity is kept as removed, so the old session's inbox tasks do not bring back a stranger. Invariants, with tests: **the new session never shows in the office until it has taken over** (its pane is hidden, so it is never a stranger or a new project's lead), **the old pane is closed only once the new session runs**, **what waits for the agent is held from the start of the switch until the brief is typed**, and **a failure before the old pane closes closes the new pane and leaves the agent as it was**. A restart picks a switch up at its recorded step. `--all-from` switches every running agent on that harness one at a time and lists those it cannot switch.

A repository can describe itself in **`orchestrator.json`** at its main checkout (the project adapter, [ORCHESTRATION.md](ORCHESTRATION.md)): its key in `/api/p/:project`, integration branch, preview address, comment kinds and anchor keys, checks, reviewers, landing commands and standing lanes. The service shows it on the repository in the world state and never runs anything from it. It is read again when the file changes; a missing file is no adapter, and an invalid one is not used at all, with every problem listed (`adapterProblems`) rather than half-applied. Keys it does not know are listed and ignored. `GET /api/p/:project/queue` gives the project's own tools who works its queue: each of the adapter's `lanes` joined to an office agent (the one working in the lane's `worktree`, the one whose herdr name or Pi session name is exactly its `agent`, or both when both are given; with neither, the agent called by the lane's name), with its state, what it is doing, its branch and model. A Pi session's name is the one in its terminal title (`/name`); the Pi extension reports it, and the service keeps it per session in memory like the model, so a new session in the same checkout has not said it and a restarted office hears it again at the session's next turn or poll. A lane with `agent` never falls back to another agent, such as a Claude Code session in the same folder. A lane nobody runs in is listed `offline` with why. The comment counts stay empty until comments live here (ORCHESTRATION.md, step 5). `inbox say <name>` also takes a lane's name, after office names and teams: it reaches the same agent, so a project's tools message their lanes by the names they already use. A name that is a lane in several projects means the sender's own.

**Team status** is derived, never stored. A team is `blocked` when its lead is stuck, or when someone is stuck and nobody in it is still working; stuck means waiting at a prompt in herdr or waiting on a blocking inbox item. A crew member stuck while the lead works is the lead's to handle, so it does not reach you. Otherwise the team is `working`, `idle` or `offline`. The service announces a team through herdr's notifications once, on the change to blocked; on start it only takes note of how things stand.

**Messages** (`messages`, `message_deliveries`) are everything said in the office: your instruction to a team, an agent's message to another agent or a team, a handoff and a review verdict. They are kept like replies: never deleted, one delivery row per agent, and a client id so a retried request is not a second message. The agents a message goes to are fixed when it is given: a team's lead, or its crew (the running ones, else all) when the lead is the one speaking. A delivery is `queued` until its agent is free, then claimed as `sending` by a conditional update, so two reactions never type it twice, and ends `delivered` or `failed` (with herdr's reason). On service startup, any delivery left `sending` is marked `failed` with a warning that it may already have arrived and Retry may send it twice: a stopped sender must not reserve its agent forever, but an unconfirmed prompt is never automatically replayed or marked delivered. A failed delivery to a departed agent, or one whose pane closed during submission (including `PTY actor closed` and pane/agent not-found errors), says **left before it arrived**, without Retry. The service refuses retry for a missing/offline recipient or a closed-recipient failure; genuine transport failures to live recipients keep **not delivered** and Retry. Each agent takes one prompt at a time. What queued up while it was busy is typed as **one prompt**, oldest first, each message under who sent it and how long ago (`Alma, 42 min ago:`), headed by "N messages arrived while you were busy; later ones may supersede earlier ones. Reply once to what still matters." and closed by one footer, so an agent that was away an hour answers what still matters once instead of acknowledging each stale message in its own turn. A single message is typed exactly as it always was. The prompt is capped: the newest messages stay in full up to about 6000 characters, older ones shrink to a line of 160 characters (their `Image: /…` paths kept beside them), and at most 50 go in one prompt, the rest in the next. The deliveries in a prompt are claimed together and end `delivered` only when herdr sees the agent take the prompt up, or all `failed` together with herdr's reason; Retry puts one back in line, and those retried together are typed together again. The text of each is prefixed with who is asking, the team and the agent's part in it: a first mate is told to plan it, give it to its named crew or start more in herdr, supervise them and report the outcome; a standing team's lead to divide it among its crew. An agent **answers you** with `inbox say founder "…"`: a message marked `to_founder`, with no deliveries, so it is typed into no terminal and is not an inbox item. The office keeps your conversation with the agents apart from the rest of its talk (the latest 200), and an agent's panel shows it as a thread above the message box: what you said to it or to the team it leads, and its answers. Your messages tell the agent to answer in a sentence or two and to follow up the same way when the job is done or something new happens; decisions still go to `inbox decide`. No agent can be named "founder".

**Office notices to the founder.** The office can put a line in the same founder conversation as agents' answers: `from_office` and `to_founder`, clearly labelled **The office**, associated with the agents concerned but with no terminal deliveries. It also attempts one herdr desktop notification per committed notice. Every reaction (including the 30-second poll) observes queued deliveries: if an agent is idle or done and its oldest queued delivery has waited **more than ten minutes**, it reports “agent (project) is free but N messages have waited M minutes undelivered.” N is the whole queued count; M is the oldest wait in whole minutes, measured from the delivery's queue/Retry time. One durable latch per agent suppresses repeats until its queue drains; the latch and notice commit together, so a restart does not announce the same episode again. This watchdog only observes: it never changes, claims or retries a delivery.

**Tell all leads** (`POST /api/world/all-leads/messages`) is one founder instruction with one fixed delivery per selected project or standing-team lead. Omit `leadIds` for all current leads, or send the checked lead ids; stale selections are refused before anything is stored. A required `clientId` makes retrying the entire broadcast idempotent, and the instruction and all deliveries are committed together. It uses the normal team instruction prompt and image paths. Offline leads remain queued and are listed in `queuedOffline`; teams without a lead are listed in `skippedTeams`. Both the office's Projects panel and the Projects board open the same checked-recipient composer. Each recipient's conversation and project thread mark it as an all-leads broadcast; their `inbox say founder` answers remain in those threads (not guessed to belong to a particular broadcast).

**Acknowledgment loops** are advisory, never a sending limit. Eight alternating, single-recipient agent messages under 300 characters within ten minutes queue one office notice to both agents to stop replying to acknowledgments and continue the work; every original message still goes through normally. The pair's episode and notice latch survive restarts. Ten minutes of silence, a handoff/review, a longer message, an image or a group exchange ends that episode; repeated senders break the alternating streak but do not rearm a notice. Founder and office traffic never count. A second trip by the same pair within 30 minutes sends one office-to-founder notice; further trips do not repeat it until more than 30 minutes pass between trips. The recurrence latch survives restarts.

**Work** (`work`) is finished work handed to another team to review: the team named, or the one the sender's team `handsTo`. It is `in_review` until that team (and only it) answers `accepted` or `changes_requested`; changes need notes. The verdict is a message back to whoever handed it over, and handing the same work over again starts its next round. The service decides nothing about the work itself: whether it is good is the reviewing agents' judgement.

**Usage** (`usage.ts`, `usage_readings`; `WorldState.usage`) is the founder's subscription use: a meter per limit (Claude's 5-hour window and week, Codex's week, and Codex's 5-hour window once a plan reports one) and each agent's and team's tokens this week. **No model and no account endpoint is ever called for it**: a meter is what the provider already said in the headers of a reply an agent was getting. Claude Code hands its plan's limits to its statusline command, so a Claude Code session the office starts gets `inbox statusline` in the same `--settings` as its hook (left out when the settings read there set a statusline of their own; nothing is written to anyone's settings), which posts them to `/api/agent/usage` and prints a short line. Pi's extension forwards Codex's `x-codex-*` headers from `after_provider_response`, and the newest codex CLI rollout's latest `rate_limits` are read lazily. Claude Code's own cache of its last `/usage` read (`cachedUsageUtilization` in `~/.claude.json`) is the fallback, shown with its age. One reading is kept per meter, and an older reading never replaces a newer one. A reading over 30 minutes old is `stale`; a window that has reset since its reading shows 0% and stale (the week keeps its weekday and hour; a 5-hour window's end is unknown until the next reading). Tokens (input, output and cache writes; cache reads left out) come from the session files each harness keeps: Claude Code's transcripts and their sub-agents' (a streamed reply is counted once), Pi's session files (its Codex replies count against Codex, its Anthropic ones against Claude), Codex's rollouts (a repeated count once). They are read a slice at a time in the background, from where each file was left, so drawing the office never reads a file. A session belongs to the agent whose current session it is, or to the one agent of its harness in that folder, and to the team whose worktree (or other worktree) holds its folder. An agent's or team's `share` is an estimate: its part of a provider's weighted tokens this week (output weighs most, a cache read least) times that provider's weekly meter, so the parts add up to the meter; it is null when no reading belongs to this week. Use from other devices is not in the session files here, so on Claude it lands on whoever ran here.

**The founder's rule near Claude's 5-hour limit**: while the crew guide's switch is Mix and a fresh reading (under 30 minutes, window not reset) puts Claude's 5-hour meter at 90% or more, the guide (`inbox crew`, a lead's `inbox team`, and the lead a new project starts with) treats Claude Code as switched off and gives each rule's Pi backup, saying why and until when. The founder's saved setting stays Mix, crew already running carry on, and switching an agent is not affected. On "Claude Code only" or "Pi only" it changes nothing. With no reading, nothing is paused.

**Activity** is what an agent is doing right now (its current tool, as one line) and its **helpers** (sub-agents). It comes from the harness: Claude Code through an HTTP hook (`/api/hooks/claude`: PreToolUse, SubagentStart/Stop, Stop), Pi through its extension (`/api/agent/events`). It is kept in memory only, because it describes the last minutes: a tool line fades after two minutes, a helper nobody hears from after thirty, and a finished turn clears both. Activity changes are broadcast but never make the service react, so they cannot trigger a delivery. The **model** an agent runs is reported the same way, for the session that reported it: Claude Code's from the hook input's `model` (SessionStart, through `inbox hook claude`) or its transcript's latest reply (read at each Stop, or when none is known yet), Pi's from `ctx.model` at session start, on `model_select` and at each turn's end. When a harness has not reported it (a Pi agent started before the extension did, Codex, Claude Code without the hooks), the service reads the session file the harness itself keeps: Pi's session file (its latest `model_change` or assistant message), Codex's rollout (its latest `turn_context`), Claude Code's transcript. That read is lazy, when the office is drawn, and repeated only once the file has grown and at most every ten seconds; what the harness reports wins over it. Every path names the model the same way, specific rather than a family ("Opus 5.5", "GPT-6"), with the raw id beside it; the office shows nothing when no model is known.

**Effort** is session state, separate from a requested change. A live integration advertises `capabilities.changeEffort` and its model's accepted levels; the office's agent panel shows only those choices and the Projects board shows the reported level. Pi polls `/api/agent/effort`, waits until idle, calls its real `setThinkingLevel` API (session-only, never the configured default), and reports `getThinkingLevel` plus the request id. `thinking_level_select` also reports changes made in Pi itself. Requests belong to the exact harness/session, are applied once per integration instance, and stay pending until acknowledged; a different/clamped level or no confirmation within 30 seconds is a visible failure. The reported level is never optimistically changed. The installed Claude Code's `/effort` command accepts low/medium/high/xhigh/max but persists all except max as that model's default in user settings. It is deliberately **not offered**: no verified local session-only control exists, and restoring shared defaults afterwards would race other sessions. Its capability carries the explanation; the UI never branches on its vendor. No effort control types terminal input or starts a model turn.

**Unpresented work.** Each submitted or revised milestone and try records the assigned project's worktree HEAD on the item and its revision; the latest submission is the project's presented point, whoever on the crew posted it. Decisions also capture HEAD to recognise a pending question, but do not advance that point. Every minute, git counts commits reachable from the worktree HEAD but not from either the main checkout's HEAD (its base branch) or the presented point. Counts are cached by those three commits; neither a merge into base nor a new presentation needs a new worktree commit to clear the count. Projects show a neutral “2 commits not shown to you yet” on the board and in the office panel. Standing teams are excluded.

When a lead has been continuously idle or done for five minutes, with neither the lead waiting on the founder nor its team blocked, unpresented commits cause an ordinary `from_office` message to that lead, delivered by the existing guarded terminal path. It asks for a milestone now (screenshots, pages or video, even before the whole project is done), or a one-line explanation with `inbox say founder`. No reminder is sent with an unanswered item at current HEAD (including snoozed items). The per-project 30-minute cooldown and last reminded HEAD survive restarts; a say-to-founder by the reminded lead after that reminder suppresses it for that HEAD until a new commit. A restart begins a fresh five-minute idle observation, never guesses that an offline lead is free. This detects unshown commits, not whether the work is good or finished; no model is involved.

**A whole team idle.** Independently of commits, a project whose lead and every crew member have been continuously idle or done for five minutes gets an office reminder to present finished work, ask the founder for what is missing (`inbox decide`, with options or an open question), or say what happens next. Nobody may be at a prompt, blocked, offline, unknown or waiting on the founder. Any unanswered project item (at any HEAD, including snoozed and legacy items) suppresses it, as does the lead saying anything to the founder since that idle episode began. It is sent only once until someone on the team is observed working again: a prompt, changed crew or service restart does not rearm it. The latch, explanation cutoff and last reminder time survive restarts; the five-minute observation starts afresh. Both reminder rules share a 30-minute per-project cooldown and produce one combined office message when both apply. The unpresented-commit rule still operates independently, including while crew work.

**Headless browsers** are the one thing the office watches outside herdr and the inbox, because an agent's forgotten browser (a script's, or a dev server's probe) can take the machine's CPU with nobody noticing. Every 15 s the service reads `ps` and finds browsers a program started: a headless build, `--headless`, or a Playwright or Puppeteer profile; a browser you use yourself matches none of these. Each main process is grouped with everything under it (pages, GPU, network) and summed. It belongs to the project whose worktree (or the agent whose folder) holds the working folder of the nearest process in its lineage, read once per process with one `lsof` for all new ones (`/proc` on Linux), else to nobody. A browser is **forgotten**, and closed by the office itself, when its starter has exited (its parent is launchd or init, or gone from the list) for a minute while its project has had no busy agent for that minute (a browser of no project: while it uses under 5% CPU), or when it is over 10 minutes old and its owner has done nothing with it for 10 minutes: its project has had no busy agent (counted from when the office saw it), or, for a browser of no project, it has used under 5% CPU. A browser keeps the project it had while its starter lived. One whose project has a busy agent is never forgotten, orphan or not: it may be mid-screenshot, or detached on purpose and reused over a debugging port. The office sends SIGTERM to the main process and, if that same process (same pid, parent and command, read from `ps` again) is still there 10 s later, SIGKILL to it alone; it then tells the project's lead once, as a message from the office (`from_office`: no sender, typed as "[From the office]", never shown as yours; a project hears at most every 15 minutes), and counts it for a quiet "Closed N forgotten browsers today" on the Projects board (in memory, since the service started). One that cannot be signalled, or outlives SIGKILL for 45 s, is listed with the warning for the founder instead. A browser that may still be in use is only a warning, shown when together they use over 150% CPU for a minute or more than five run; it is kept in memory only, and Close is the founder's click. Invariants hold, with tests: **only forgotten headless browsers are closed automatically, nothing else, ever**, and **only a listed headless browser's main process is ever signalled** (Close and the automatic close alike): the process list is read again, any pid that is not a headless browser's main process in it is refused, and a browser of a working project is not closed automatically. A flagged (hot) browser for three minutes is told to its project's lead once, as above.

The office draws all of this from the same state, without storing anything of its own. Its corners stand on a **ring round your desk**, each facing it, so every team is about as close to you as any other: the first straight ahead, the next alternately right and left, then the lounge. They stand side by side from the front until the ring is full, so a new team takes the next place without moving anyone; after that the ring widens just enough for all of them to fit evenly, and nobody changes sides. People walk round a path inside the ring and in to where they are going, so no walk crosses a desk or another corner. A message that arrives while you watch becomes a **visit**: the sender walks to the first recipient, says it in a speech bubble (carrying a folder for a handoff) and walks back. Your own instructions are bubbles over the agents that hear them. A blocked team is standing state rather than an event: its running lead stands at your side of the desk, facing you, for as long as the team is blocked, and a card offers what fits (the answer card for a decision; for someone at a prompt, who it is, a message asking the lead to handle it, or their panel). The office offers no allow or deny, since it cannot see the prompt. Sending the lead back holds until who is stuck, or why, changes; it is kept in the page only. The `handsTo` links are arrows between team corners, round the desk just outside the path. The **board** (`#/teams`) shows the same projects, work and messages as columns and lists.

The other layout, **Building**, puts the same teams in bays round an open hall. Its middle is an indoor garden rather than a desk: agents on no project spend their idle time there, on benches or strolling round a walk, and keep to its paths. At the garden's front is a paved clearing where you stand: a lead who comes to you stands there facing you, and agents waiting for you gather beside the way in, in order, without ropes. The garden is planted thick (trees of several kinds, shrubs, ferns, grasses and flowers, a pond with reeds, lilies and ducks), but nothing grows on a path, the clearing, a bench or the gravel beside one, and nothing tall stands between where "Your desk" puts you and the clearing; the tests hold it to that.

The queue at your desk is `needsYou` from the inbox, one place per agent. The office never shows an agent's terminal: you read what they are doing and what was said, and a message to one agent goes through the same deliveries as everything else. herdr's own errors reach the UI as one line.

## Codex

Codex posts through the CLI and receives by **pull** today. Two routes could make it boundary or live; each needs a check against the installed Codex before building on it:
1. **Codex hooks** (a Stop-style hook). This would reuse the Claude hook's shape.
2. **`codex queue --thread <id>`** to push a follow-up into a running thread. This would give live delivery without a terminal.

Also unconfirmed: that Codex exports the thread id to tool shells as `CODEX_THREAD_ID`. Until that is checked, run the CLI with `--harness codex --session <thread id>` or inside herdr, which resolves the pane.
